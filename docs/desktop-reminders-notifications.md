# 桌面对话提醒与通知播报修复（2026-10-27）

## 定制通知漏收与开发版自启动补充

本机 18:23 启动的开发进程能记录 Codex 通知接收与播报开始，但没有对应的服务端
定制通知接收记录；用户确认同时手机已收到。这说明该次问题发生在电脑收件之前，
不能据此断言是音量、语音模型失败，也不能仅凭本地日志确定线上是旧版本还是多实例路由问题。

- 保留实时同账号 fanout；增加 `desktopNotificationsV1` 能力与只读 `notification_sync`。
  电脑绑定且配对证明就绪后立即查询，每 15 秒恢复本次应用运行期间、最近 10 分钟内的
  已投递通知。查询走当前电脑所在的控制连接，不依赖调度进程持有它的内存 WebSocket。
  只读现有投递账本，不能创建消息、修改手机已读状态、开启通知偏好或启动电脑工具。
- 后端强制当前绑定租户/用户、可用来源角色和已投递状态；排除 `desktop_task` 回流。
  最多检查最近 100 条，响应限制在 48 KB 内；多条同角色仅校验一次，按创建顺序进入播报队列。
  不是无限离线回放、持久语音送达或高流量通知的可靠队列。
- 推送与恢复共用去重，额外保留服务端通知的去重窗口，避免自动任务进度冲掉去重记录。
  定制通知在有界队列中优先于任务汇报；形象未就绪、隐藏、忙碌、积分不足等等待原因明确可见。
  不确定的已开始语音仍不自动重放。设置页显示通道状态、旧后端不支持、需重新扫码或通知关闭。
- 源码 `npm start` 的 `app.isPackaged=false`，按原约定不会登记开发 Electron。
  开关明确标注“仅安装版”，展示安装 EXE 后启用的说明，不伪装成可操作开关。
  安装版按 `launchItems` 匹配当前用户的 `ControlDeviceTest`，避免与 AppUserModelID 混淆；
  保存了开启偏好但注册项丢失时恢复，系统明确禁用的已有项不强制重开。

需要同步部署上述后端并重启桌面源码进程；只更新桌面不能让旧服务具备恢复接口。

## 已定位原因

1. 原桌面只有定时任务设置页，没有 Harness 提醒工具；命令识别未覆盖“明天九点提醒我”等句式，
   容易普通回复而没有实际保存。原后端没有处理桌面表单的 `desktop_action`，也未声明能力。
2. 原队列在调用 speak 前就移除通知，忽略 `{ok:false,code:SCORE_PENDING}`；本地已复现
   “调用一次、队列归零、事件已去重”，导致未就绪时丢失播报。
3. 后端本来已有绑定电脑的 `ControlNotificationFanout`。线上是否触发、接受目标数仍要查部署日志；
   本机旧日志没有 notification 诊断，不能据此断言线上没有下发。

## 源码修复

- Harness 增加 `control_reminder`，支持单次/每日、查询、按真实列表编号删除。
  仅用户原始任务明确要求提醒时才可调用；文件/邮件/工具结果及通知不能授权创建提醒。
  账号、租户、角色、本机时区由宿主提供，模型不能选择其他账号。
- 提醒命令统一进入 Harness，Worker 收到当轮本机时间以解析相对日期，模糊时刻要求澄清。
  不使用 shell、Codex、WorkBuddy 或本地内存计时器。服务精度为分钟，支持单次/每日。
- 服务端新增 `ControlDesktopMemos`，由当前绑定 HMAC 证明保护，能力 `desktopMemoV1`。
  只开放 memo_create/list/delete，复用原 `ProactiveMemoManagementService`、账本与持久化；
  不宣称其他未接入的桌面服务可用。设置正确租户线程上下文，并 finally 恢复。
- 同轮同参数使用稳定请求 ID；保存结果含真实 id/status 才确认。超时说明未确认，先查询再重试。
  客户端停止不能撤销服务端已接受的创建。账号通知关闭返回 notificationsEnabled=false，明确告知不会播报。
  不擅自开启通知偏好、主动消息计划、服务端开关或立即发送权限。
- 通知立即进入实时信息，使用当前角色播报、不切换角色。SCORE_PENDING、CHAT_BUSY、TEXT_ONLY
  等明确未开始的结果保留待播；未知结果或已开始的生成不自动重播。仍保持最多 16 条、10 分钟
  有效窗口、去重与换绑清理；零积分只展示文字、不生成收费语音。
  新 notification.received/delivery 日志只记录状态元数据，不含通知正文。
